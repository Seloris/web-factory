# Changelog

Why each rule of the process exists. A rule changes with the case that motivated it; the entry says which. Newest first.

## 2026-10-21 — selo-flow 1.0.0: two lanes, living specs, the base branch shared

The review of 46 claude-companion sessions found the same costs again and again: a small request went through a spec, a plan and four commits; a squash swallowed another session's commit; an autopilot stopped on a dirty tree that was not its own; specs grew a history nobody read and drifted from the code once a request skipped them; the browser test hit the person's own servers; `retro` was never run. The proposal and the plan that answer it are in the repository's `docs/revamp-1.0.0/`.

- **The factory is renamed selo-flow.** The plugin `selo-flow`, its board `selo-flow-board`, the marketplace `selo-flow`, the prompts `/selo-flow:…`, the manifest `selo-flow.yaml` (its first line `selo-flow: {version}`), `factory-init` renamed `init`, the board's export folder `~/.claude/selo-flow-board/`. One name everywhere.
- **Two lanes.** The fastlane (`/selo-flow:implement {request}`) codes a request with no spec step and no plan, its spec delta in the same commit, one commit per component; the feature lane writes the spec, the plan and the stages. `autopilot` reads the code first (an `Explore` subagent, writing nothing) and picks the lane: the fastlane for one component with no new business rule or entity; ` — fastlane` and ` — with plan` force it. A fastlane that meets a new rule or entity stops before its commit.
- **The spec follows the code.** A spec describes an area (a screen, a route, a domain) as it behaves today, in the present tense: no `Status`, no `Updated`, no decisions section (two sessions fought over the date line). Every change of behaviour updates its area's spec in the same commit, without asking when it restates the request; an area with no spec gets a three-line stub, never the question "do we create the spec?". New FRs are `(planned)` until built; a replaced FR is deleted and its id put on `Retired:`. `write-spec {slug} — rewrite` brings an old spec to this shape once.
- **The `Spec:` line and `spec-check`.** Every code commit carries `Spec: {slug} +FR-48 ~FR-13 -FR-07` or `Spec: none ({reason})`, checked by `scripts/spec-check.mjs` (duplicate, retired or missing ids, the FRs still `(planned)` at a plan's end, the next free ids). A `PreToolUse` hook on `git commit` warns, never blocks, on a code commit without the line, on `-a`, `git add -A`, `git add .` or `--amend`, and on a spec whose ids fail: free sessions cannot run the script from their `CLAUDE.md`, and the 16 October hooks had shown that a refusal costs a round trip on every false positive. `review {slug}` checks a whole area against the code.
- **No branches, no squash, one review.** Everything is committed on the base branch, each commit naming its files (`git commit --only`), never `-a`, `add -A` or `--amend`; a file another session is editing is waited for, then left; a dirty tree no longer blocks; a test failing outside the work's files is marked `[-]`, not investigated. These rules sit in a tagged block of the project's `CLAUDE.md`, so sessions without a skill follow them. ` — with review`, ` — final review`, ` — close the branch` and the squash are gone: the last stage reviews the whole work once; `/selo-flow:review {plan folder}` settles what it left open.
- **Decisions in two lists.** *Business decisions* (at most five, what the person would want to check) then *Technical defaults*, in the plan in every mode, in the commit body and the report in the fastlane. `grill-me` asks through the session's question tool, the recommended answer first, two rounds at most, the rest left as `Q-NN`.
- **The browser test runs on the demo.** `commands.demo` and `demo_url` start seeded data on their own ports, in the background, under `{git-common-dir}/selo-flow/demo.lock`, and stop after the test: the person's servers and data are never touched, two sessions never share a demo. It runs by default on the last stage; ` — without browser test` skips it. `wt.exe` and "never restart a server" are gone. The `react-express` pack ships `npm run demo` (in-memory PGlite seeded by `src/seed/demo.ts`, Vite in the `demo` mode with `--force`) and allows Vitest on the front's pure `.ts` modules.
- **`init update`.** The plugin's parts of the root `CLAUDE.md`, `docs/CONTRIBUTING.md` and `.claude/rules/memory.md` sit between `<!-- selo-flow:begin {id} -->` and `<!-- selo-flow:end {id} -->` tags; `init update` rewrites them, overwrites the plugin's own files, adds the missing keys (the manifest's version, the settings with the old `factory` ids renamed), renames `factory.yaml`, and never touches code, specs or plans. A project from before 1.0.0 is rewritten once, read through `git diff`. `samples/todo-app` is updated this way.
- **The push deny rule matches.** The sample's fastlane trial showed Claude Code reading `Bash(git * push:*)` as a literal prefix (the `*` is not expanded before `:*`): the rule never matched `git -C x push`. `git * push*` would match, but also every commit whose message says "push". The template, this repository and `samples/todo-app` now deny `git push:*`, `git -C * push*` and `git -c * push*`; `init update` replaces the old form.
- **What the branch's review fixed.** A plan's review took every commit since its `plan.md`, other sessions' included: it now takes the plan's commits, those with its scope (`workflow-rules.md`, **Where commits go**). An unknown key under `models` or `language` is warned (an old `advisor:` survived silently), so is a `demo` without `demo_url` (the browser test then falls back to the dev servers). `spec-check --plan` on a folder with no `plan.md` exits 2 with a message instead of a stack trace. The commit hook also reads the files a `git add` stages in the same command. `grill-me` says what `write-spec` does: it runs on a new area. In the project's `docs/CONTRIBUTING.md`, only the process steps are the plugin's block; the conventions are the project's, and say the `Spec:` line. `init update` keeps a placeholder the manifest does not hold (`{{ui_language}}`).
- **Removed.** `retro` (never used: the plans' Deviations carry the lessons), the `advisor` role (nothing applied it), the parser's silence on an unknown key (now a `warnings` entry). The board's entries moved to its own `CHANGELOG.md`: their version numbers collided with the plugin's.

Projects: remove `factory@webapp-factory` and `factory-board@webapp-factory`, add the `selo-flow` marketplace, install `selo-flow@selo-flow` and `selo-flow-board@selo-flow`, run `/selo-flow:init update`, then open a new session. Version 1.0.0.

## 2026-10-21 — A free request answered without a commit carries a recap too

- **The done footer without commits, off the workflow.** A session of claude-companion worked on a free request and ended its turn without a commit, so with no footer, and the board exported its off-workflow run `awaiting-answer` with no recap. The companion had nothing to show for a session whose job was done. A free request (no skill) answered without a commit now ends with the footer too, its `> ` recap line alone; a commit question, a failure or an open question still ends with none, and a skill's turn keeps the footer for its commits. The board already reads a footer with no commit line (`commits: []`, phase `job-done`). Projects initialised earlier get it by replacing the `**Done footer.**` paragraph with the one of `templates/CLAUDE.md`; `samples/todo-app` has it. Version 0.8.0.

## 2026-10-20 — A free request ends with the done footer too

- **The done footer in the project's `CLAUDE.md`.** A session of claude-companion asked to rework a tile's design, outside the workflow, committed and stopped on "nothing was pushed": no `## ✅ JOB DONE`, so the board recorded its run with no recap. The rule already covered a direct request, but it lives in the workflow rules, which only a skill reads. The project's `CLAUDE.md`, always loaded, now carries it, as it carries the servers' rule. Projects initialised earlier get it by adding the `**Done footer.**` paragraph of `templates/CLAUDE.md`; `samples/todo-app` has it. Version 0.7.1.

## 2026-10-20 — The done footer carries a recap

- **A `> ` recap line under `## ✅ JOB DONE`.** The companion app shows where each session stands (at work, waiting for a commit's yes, waiting for an answer, job done) and, once a job is done, what it achieved. The footer's commit subjects are in the repository's language and say what changed in the code, not what the person got. The footer now opens with one line in the chat language, 120 characters at most, read by the board (`factory-board` 0.11.0, export `schemaVersion: 2`) from the turn's final text, as are the commit question's closing code block and the footer itself. A footer without the line still works: the companion falls back to the commits. Version 0.7.0.

## 2026-10-20 — Servers start in Windows Terminal

- **Every server in a Windows Terminal tab.** A server an agent started ran as a background command of the session: the person could not see what was running, its output was hidden, and it died with the session. The person wants everything open in their terminal. The workflow rules' new **Starting a server** section says how any server is started: where `wt.exe` is on the PATH, in a tab of one Windows Terminal window, `factory`, titled after its component (`wt -w factory nt --title {component} -d {path} cmd /k "{serve}"`); `cmd /k` keeps a crashed server's tab open on its error. Elsewhere, the background command as before, so the plugin keeps working off Windows. The agent cannot read a tab's output, so it polls the server's address and, when it stays silent, sends the person to the tab. `test-in-browser` follows the rule; the project's `CLAUDE.md` carries it too, since a plain "start the API" loads no skill. Projects initialised earlier get it by adding the `**Servers.**` paragraph of `templates/CLAUDE.md`; `samples/todo-app` has it. Version 0.6.0.

## 2026-10-20 — A place for ideas

- **`.planning/ideas.md`, the ideas of a project.** The person often has ideas for a project and nowhere to put them: a spec is too early, the technical debt is for what is wrong, and the memory is for facts. `factory-init` now writes `.planning/ideas.md`, dated items grouped by scope (one section per component, feature or `app`), so the ideas of one area read together, and the project's `CLAUDE.md` (always loaded) tells every agent to append an idea there when the person asks, and never to act on it. Only the person removes an idea, once it has become a spec or been dropped: no skill of the workflow edits the file. Projects initialised earlier get it by adding the file from `templates/ideas.md`, the `## Ideas` section of `templates/rules/planning.md` and the `**Ideas.**` paragraph of `templates/CLAUDE.md`; `samples/todo-app` has them. The factory keeps its own at the repository's root, `IDEAS.md`. Version 0.5.0.

## 2026-10-20 — The retro: each session draws its lessons

- **`retro`, an After Action Review per session.** Nothing in the workflow asked what went well, what went badly and what to change, so a correction the person made in one session was made again in the next. The person wanted the repository to improve itself at every session, after the US Army's After Action Review. `/factory:retro` answers its four questions from the session's evidence (the plan or the agreed approach, the commits, the failures, the reviewer's findings, the person's corrections) and writes `.planning/retros/{timestamp}-{name}.md`: at most five lessons, each with its evidence, its one destination and the exact change, status `open`. A session that taught nothing writes no file, so no lesson is invented.
- **One folder, with or without a plan.** A section of the plan would have missed most sessions: the default path has no plan, and a past plan is never edited. One file per session, not one shared list, so two branches never collide on its last line.
- **Recorded now, applied later.** The retro applies nothing: one session is one data point, and a rule written from it alone may be wrong. `/factory:retro apply` takes the open lessons of every retro, groups the duplicates, proposes each change on the person's yes and records its status. A lesson for the factory is never applied in a project, whose plugin runs from its cache: it becomes a proposal the person carries here, `forwarded`.
- **Offered, never forced.** `/factory:retro` is the last next prompt of every step (the rule is in the workflow rules' `## Next prompts`), and `autopilot` gives it in its report; no hook runs it in the background, whose untriaged candidates pile up. Projects initialised earlier get the `retros/` folder by updating their `.claude/rules/planning.md` from the template; `samples/todo-app` has it. Version 0.4.0.

## 2026-10-19 — Autopilot: one command to developed code

- **`autopilot` chains the workflow with no click.** Every step was interactive (the grill's rounds, the spec's and the plan's yes, one stage per session with its questions), so a feature took a person at the keyboard from the spec to the last stage. The person wanted to launch one command and come back to a finished branch. Separate sessions cannot chain themselves in the desktop app, so the chain is made of fresh-context subagents in one session (CLI, desktop and cloud alike): the spec, the plan, each stage, the final review, each on its role's model, each committed before the next starts. It starts from a request, a slug with a spec or a plan folder (resumed at its Progress), stops early on ` — until spec` / ` — until plan`, and tests in the browser only with ` — with browser test`.
- **Autonomous mode of the skills.** `write-spec`, `write-plan`, `grill-me` and `implement` take a ` — autonomous` marker, sent only by `autopilot`: no question, every `grill-me` question answered with its recommendation (now mandatory, or an explicit `no recommendation possible` with the reason, which stops the pipeline with nothing written), every default taken, and a `## Decisions taken autonomously` section in the spec and the plan as the person's record. The hard rules hold: never push, integration tests `[-]`, the squash proposed as a prompt and never run, stage commits with the Progress subject. The rule is in the workflow rules (`## Autonomous mode`), and the subagent rule now allows a subagent that has the Agent tool to spawn `reviewer` and `runner`.
- **Prerequisite.** The session must run in the `auto` or `acceptEdits` permission mode with the components' commands allowed, else the subagents stall on their first prompt; the skill says so before its first step.

## 2026-10-19 — The spec opens the feature branch

- **`write-spec` proposes the branch.** A spec written on its own, on the base branch, was committed there: only `write-plan` and `implement` created the feature branch, so a feature started by its spec left `docs({slug}): spec` on `main` and the plan found a branch to cut with the spec already behind it. Designing a flow where one session orchestrates the spec, the plan and the stages on the current branch made it visible: the first step must settle the branch. `write-spec` now does what `write-plan` does: on the base branch, its commit confirmation names a new `feat/{slug}` and creates it on the yes; on another branch it stays there. Called mode is unchanged: the caller holds the branch. `.claude/rules/planning.md` names it among the branch creators; projects initialised earlier update it from the template, `samples/todo-app` has it.

## 2026-10-19 — Plan finalized replaces the branch close

- **A plan is finalized on its own.** The board's last step, « Clôture de la branche », waited for a prompt the person had to send, and the board could not see the squash happen: on `samples/todo-app`, a home plan with every check done stayed « à fermer ». The person wanted the end of a plan to be automatic and named after the plan, not the branch. A plan is now finalized once every stage of its Progress and its Validation's `Review` are ticked; the board reads it from `plan.md` (`plan finalisé`), and its timeline ends at « Revue finale ».
- **The optional items no longer hold a plan back.** `Tests`, `Browser test` and `Integration tests` may stay `[ ]` (not run), be ticked, or be marked `[-]` (declined): the checklist still records which. Only `Review` is never skipped.
- **The squash is proposed by the step that finalizes the plan.** The last stage (when its review ticks `Review`), the final review or `/factory:review {plan folder}` proposes it after its own commit, with the same checks and the message in a code block, on the person's yes; without a plan, the last stage does. The procedure moved to the workflow rules (`## Plan finalized`), shared by `implement` and `review`. The board does not track it; `— close the branch` stays for a squash the person put off. Projects initialised earlier get the rule by updating `.claude/rules/planning.md` and `docs/CONTRIBUTING.md` from the templates; `samples/todo-app` has it.

## 2026-10-19 — The docs catch up with the skills

A review of the repository before its first real project found rules the skills had left behind.

- **The review per stage is optional everywhere.** `implement` ran the reviewer only on ` — with review` since 2026-10-17, but the workflow rules, the project `CONTRIBUTING.md` template and the root README still said "before every stage commit". The three now say what the skill does: on request after a stage, always at the plan's final review.
- **A clean `/factory:review` counts.** It never ticked the plan's `Review` item, so the final review ran the reviewer again on the same code. `/factory:review {plan folder}` now reviews the plan's implementation and, when nothing is left, ticks `Review` and proposes its commit; the final review then settles only the other items. The findings still live in the session only: the fix prompt runs there, or gets them pasted.
- **`architect` and `senior-dev` are gone.** They wrapped `write-spec`, `write-plan` and `implement` in a subagent, and those skills ask the person at every decision (the grill offer, the commit's message, the explicit yes), which a subagent cannot: they either stalled or skipped the yes. Their reason, the model guard, went on 2026-10-16; the session runs the skills on the model the person picked. `reviewer` and `runner` stay.
- **One model per role instead of a `premium` preset.** The premium set (Fable for planning and review, Opus for the code) fitted nobody as a block; `factory-init` now asks for each role with the `standard` preset as the recommended answers, and writes the map of the changed roles only. `premium` is no longer a known preset.
- **No stack word in the plugin's docs.** `docs/manifest.md` showed a `.NET` component and `factory-init` named its files, against the rule of this repository's `CLAUDE.md`; the examples are now the `react-express` pack's commands.
- **The sample carries the current contract.** `samples/todo-app` was initialised before `serve` and `serve_url` and before the `Tests` Validation item; it has them now.
## 2026-10-17 — The browser test starts the servers

- **`test-in-browser` starts the local servers that do not answer.** At the browser test of `samples/todo-app`'s home plan both servers (api, web) were down; the skill could only hand the start commands over and wait, so the person had to authorise the start by hand, and asked for the default to be reversed. The skill now checks the tested component and the components it `needs`, starts each silent one in the background in stage order, waits for it to answer (bounded, then reports its error and stops), never touches a server that already answers, and says in its report which servers it started and left running.
- **The start command is in the manifest.** A new `commands.serve` and a `serve_url` per component, read by `scripts/manifest.mjs` (`serveUrl`, defaulting to `url`), rather than a command picked out of the "Local run" prose: the parser stays the one reader of how a component runs. `serve_url` is not `url`, which makes a component browser-tested. A component without them (projects initialised earlier, `samples/todo-app` among them) falls back to its `CLAUDE.md` "Local run" for both the command and the address, and the report suggests adding the keys; with no address at all the server cannot be checked, so the skill asks. The `react-express` pack chains the migrations before the API's dev server (`npm run db:migrate && npm run dev`): `serve` only runs when the API is down, which is when PGlite allows a migration.

## 2026-10-17 — Commit messages proposed before the commit

- **Every commit question shows its message.** The pack's commit was asked as a bare "commit?", and the person only saw the message once it was in the history, too late to correct it cheaply. A request to approve a commit now shows the exact message in a code block, and the yes covers both. The rule is in the workflow rules (`## Commits`), in the template of a project's `CLAUDE.md` (for requests made outside a skill), and in this repository's `CLAUDE.md`.
- **Stage subjects are announced with the plan.** A stage commit is made without a question, so its subject is now written beforehand: a `Commit:` line under each stage of the plan's Progress, approved with the plan, or the approach without a plan. `implement` uses it and says so when the work made it change. Projects initialised earlier get the `Commit:` line by updating their `.claude/rules/planning.md` from the template.

## 2026-10-17 — A TypeScript pack replaces the .NET / Angular one

- **`react-express` replaces `dotnet-angular`.** The next projects are full TypeScript (React front, Express API), and a pack is only worth keeping for a stack a project uses; the .NET / Angular pack stays in git history (last present in `7fdb9ac`). The workflow does not change: the same `handoff` / `prepare` pair carries the API contract to the front (OpenAPI generated from zod, types generated with `openapi-typescript`), and the same table-driven skills read their facts from the component's `CLAUDE.md` (`drizzle-migrations` for `ef-migrations`, `write-api-tests` for `write-integration-tests`, `openapi-client` rewritten).
- **PostgreSQL through PGlite for local runs and tests.** The database had to run with `npm ci` alone, on Windows, for anyone trying a project: PGlite is PostgreSQL in WebAssembly, in the Node process, with no Docker and no native build; deployment uses a real PostgreSQL with the same migrations. SQLite was set aside: its drivers need a native addon or a given Node version, and moving to PostgreSQL later means rewriting the migrations.
- **Route tests run with the fast suite.** They hit an in-memory PGlite, no external system, in seconds: the reason integration tests never run unasked does not apply, so they belong to the api component's `test` and run at the end of every stage. The pack declares no `integration_tests`; the rule still holds for tests that reach real systems.

## 2026-10-16 — The lead chooses its subagents

- **The two hooks are gone** (`require-runner`, `delegate-exploration`, with the manifest's `hooks:` switches and `FACTORY_ALLOW_INLINE_RUNS`). `require-runner` denied a one-line `find` to the lead working on the plugin itself, and every denial costs a round trip and a workaround; the exploration counter denied the fifth `Grep` of a search that needed six. The model knows when a full test suite or a build would flood its context, and the workflow rules now say what each subagent is for (`runner`, `Explore`, `reviewer`, `architect`, `senior-dev`) and leave the call to the lead. Only the review stays a subagent by rule: its value is in having no stake in the code.
- **The model guard is gone.** Three skills checked the session's model against their role and re-spawned themselves on the right one; the person already picks the session's model, and the pane shows the one recommended for the next step. A subagent is still spawned with its role's model.
- **Integration tests: the rule, not the ritual.** They still never run unasked; the lead no longer has to quote the person's request word for word to `runner`, and `runner` no longer refuses without the quote.

## 2026-10-16 — A plugin, one project per repository

- **The repository is the plugin** (`plugins/factory/`, `plugins/factory-helper/`, their marketplace); each project is a repository of its own that enables it. Two other layouts were tried the same day and dropped: projects as separate repositories under a git-ignored `workspaces/` folder of the plugin's repository (every git command needed the project's path, the parent `CLAUDE.md` leaked into nested sessions), then a monorepo holding the plugin and the apps (a project selection in every prompt and in the pane, for a benefit no project needed yet). One project per session: nothing to pick, paths start at the root.
- **`factory.yaml` replaces the ```factory block of the root `CLAUDE.md`.** A tool reads the manifest without parsing Markdown, and the parser finds it from any folder of the project. The component block stays in each component's `CLAUDE.md`: a component keeps its instructions when it moves.
- **What goes where.** Useful to two projects or more: the plugin. Specific to one project: that project. The rule keeps the plugin reusable and the projects' quirks out of it.
- **Skills under the `factory:` prefix** (`/factory:implement`), the plugin's namespace, so a project's own skills never collide with them.
- **The pane reads the folder it runs in.** No project list, no selection: the session is the project.

## 2026-10-16 — Founding rules

Brought from the tooling of one .NET / Angular project, where each of them was learnt the hard way.

- **Never push.** An agent that pushes publishes a mistake before a human saw it; a human pushes.
- **One stage per session.** A stage spanning two components in one session ran out of context mid-way and lost track; a fresh session resumes from the plan's Progress ticks and the branch's commits.
- **Review before every stage commit**, by a read-only agent with no stake in the code: the author of a change does not see what it misses.
- **Silence is not approval.** A spec or plan committed on an unanswered summary was reworked twice; it is committed only after an explicit yes.
- **Mechanical work goes to `runner`.** Build, test and lint output floods the lead's context and buries the decision it has to make; a hook denied those commands in the lead session, and the lead read a short report. (Hook dropped the same day, see above; the advice stays.)
- **Exploration bursts are capped.** A lead reading twenty files in a row drifted from the task; past a few calls a hook sent the search to a cheap subagent. (Dropped the same day, see above.)
- **Integration tests never run unasked.** They hit real systems (databases, containers, external services) and take minutes; the person names them when they want them.
- **The spec has one writer** (`write-spec`). Specs edited from a plan or from code drifted from the business meaning; every delta goes through the skill and ships with the change that motivated it.
- **Model guard.** A plan written on the implementer's model was shallower than one written on the planner's; each skill checked the session's model against its role and delegated when it did not fit. (Dropped the same day, see above; the preset still says which model each role is meant for.)
- **Caveman voice between agents**, normal prose for the person: tokens between agents are cost without a reader.
- **Stack-agnostic skills.** The words of a stack live in `stacks/` packs and in the components' `CLAUDE.md`, never in the skills, so the same workflow runs on the next project without porting.
