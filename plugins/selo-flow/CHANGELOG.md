# Changelog

Why each rule of the process exists. A rule changes with the case that motivated it; the entry says which. Newest first.

## 2026-10-28 — selo-flow 3.1.0: writing code, the lazy way

The person (2026-10-28) wanted the code written leaner, for the tokens spent as much as for the code kept, and weighed the ponytail plugin (DietrichGebert/ponytail) for every selo project. Its hooks inject its rules into every session and every subagent (the reviewer and the runner too), and its rules ask for one small test where selo writes the tests first: its principles are kept, not the plugin.

- **The rules' new Writing code section** holds how `fastlane` and `build` write application code: only what is asked, reuse before writing (the project, the framework, the standard library, an installed package, then new code), the smallest change that works (no abstraction for one use, no option nobody sets), never cut validation, checks or tests to write less, and a deliberate shortcut recorded as a Technical default (and in `.planning/technical-debt.md` when it is debt). The two skills carried their own copy of the first two lines; they now point to the section.
- **The reviewer's Simplicity check** (tag `simplicity`): code the work does not need, an abstraction for one use, new code where the project or the standard library already does it, a dependency or a shortcut recorded nowhere. Before, nothing checked it.

Projects: `claude plugin update selo-flow@selo --scope project`, then a new session. Version 3.1.0.

## 2026-10-27 — selo-flow 3.0.0: selo is selo-flow

The person (2026-10-27): three pieces carried two names. The workflow plugin was `selo`, its ops export plugin `selo-ops`, and the dashboard beside this repository, which reads that export, was `selo-ops` too. Each piece now has its own name with the `selo-` prefix: `selo-flow` (the workflow), `selo-feed` (the export), `selo-ops` (the dashboard).

- **The plugin is `selo-flow`** (folder `plugins/selo-flow/`, install `selo-flow@selo`). The marketplace stays `selo`. The prompts are `/selo-flow:{skill}` and the agents `selo-flow:reviewer` and `selo-flow:runner`; the model hook (`agent-model.mjs`), the lane hook and the launcher (`selo-run.mjs`, which looks up `selo-flow@selo` in the installed plugins) follow.
- **Unchanged:** the manifest `selo.yaml` and its `selo:` key, the `SELO_*` settings, `~/.claude/selo/`, the tags `<!-- selo:begin/end -->`, the mockup mark `selo:mockup`, and selo as the workflow's name in prose.
- **`setup update` moves a 2.x project:** `selo@selo` becomes `selo-flow@selo` in its settings, its launcher is rewritten, and its instruction files get `/selo:{skill}` → `/selo-flow:{skill}`, `selo:reviewer`/`selo:runner` → `selo-flow:…`, `selo@selo`/`selo-ops@selo` → `selo-flow@selo`/`selo-feed@selo`. A 1.0 project's `/selo-flow:{skill}` prompts are right again.

Projects: `claude plugin install selo-flow@selo --scope project`, `claude plugin uninstall selo@selo --scope project`, a new session, `/selo-flow:setup update`, then a new session again. Version 3.0.0.

## 2026-10-27 — selo 2.16.0: ` --worktree`, and the worktree follows the work

The person (2026-10-27): a worktree was a state selo found (the branch of the session), never a choice a command could make; a command should run in a new worktree, in an existing one, or where the session is when nothing is said. And a mockup drawn in a worktree gave a `Next:` line that `pilot`, typed in another session, could not follow: the file was uncommitted in a checkout it did not see.

- **` --worktree [{name}]`** (the rules' **Choosing the checkout**) on every skill that works on the checkout: `pilot`, `fastlane`, `blueprint`, `build`, `mockup`, `review`, `try`, `run`. Absent: today's behaviour. Alone (the five that have a request or a blueprint to name it from): a new worktree named like a blueprint. With a name: the existing worktree of that name (its folder's last segment, or its branch), created under it when none exists; `review`, `try` and `run` take a name only. Read before any other check of the prompt (a mockup's or a blueprint's existence is looked for in the worktree, not where the prompt was typed: that was the stop the option is for). Entered with the session's worktree tool when it has one (its `name` or `path`), else `git worktree add {main}/.claude/worktrees/{name}` (under the main checkout, never nested) and the session's change-directory tool, else a stop that says where to open a session; the session stays there. The uncommitted files of the work (a mockup, a bootstrap) are copied there first; the lane then runs in the worktree variant and says so in one line, `Worktree {name} · branch {branch} · slot {n}`.
- **A worktree's slot** is the last one its runs took (`manifest.mjs` gives it; the slot file whose `root` it is tells slot 0 from none, as Selo Ops already reads it); `no slot yet` before its first run, or once another root took that slot; the next run may move it. Named in that line and in the `Next:` summaries, as the person asked, so a person reading the footer knows on which ports that worktree's copy answers.
- **The worktree follows the work:** a step that ends in a worktree writes ` --worktree {name}` into its `Next:` lines, before ` --autonomous`, and names the worktree and its slot in their summary (the rules' **The next steps**); a step on the base branch writes neither. The lanes' "missing mockup / missing blueprint" stops name the worktrees that hold the file.
- **A validated mockup drawn in a worktree is committed on its branch at once** (`docs({page}): mockup — {name}`, `Spec: none (mockup)`), without a question, as every commit of the worktree variant: a session that enters the worktree finds it, and the landing's squash carries it (folded into the one commit like a bootstrap). On the base branch nothing changes: uncommitted, committed by the lane with its work.
- `fastlane --iterate`'s **Where** question is not asked when the prompt carries ` --worktree`. `pilot --autonomous` enters the worktree before its first step, so every subagent starts there.
- The cheat sheet gets a **Worktrees** section. A fresh-context audit of the whole flow after the change fixed its first draft: the worktree entered before the "missing mockup" check, `review` added to the skills, a name required for `review`, `try` and `run`, the `Next:` lines of `pilot --autonomous` and of a fastlane after its landing.
- Not done here, selo-ops: its `next` entries do not carry the run's root (Selo Ops knows the run's `root` and `branch`, and the prompt now carries the name); its new-session page lists the uncommitted validated mockups only, so a worktree's committed mockup is reached through its `Next:` line, not the board; `parsePrompt` resolves a blueprint path against the session's root, so `/selo:pilot {blueprint} --worktree {name}` typed elsewhere reads no Progress until selo-ops learns the option.

## 2026-10-27 — selo 2.15.0: a status line on every turn

The person (2026-10-27): could each turn and each session end with a recap of what is going on? The done footer gave one, but only when the job was done: a turn that stopped on a question, a commit to approve or a failure said nothing of where the job stood, and nothing summed up a session.

- **The status line** (the rules' **End of turn**): every turn without the footer gives `Status: {one line}`, what is done and what is left or blocks, right before its question or its commit's code block so they stay the last text, else as its last line. The iterate loop of `fastlane` and the loop of `mockup` give it above their question.
- **The session's recap** is not written by the agent: selo-ops 2.13.0 builds it from these lines and the footers' recaps, at each `Stop` and at `SessionEnd`. No hook forces a recap out of the model: that would cost a turn each time.

## 2026-10-27 — selo 2.12.0: options as `--{name}`, subcommands as words

The person (2026-10-27): with the hints of 2.11.0 in view, why an em dash rather than a plain dash, and arguments "as /doctor does". The em dash came from prompts Selo Ops writes, never typed by hand; it is hard to type, and the options at the end of the prompt needed a mark that a request's own text would not carry.

- **Options**: `--{name}` at the end of the prompt (`--autonomous`, `--fastlane`, `--no-browser`, `--until-blueprint`, `--mockup {file}`, `--stage N`, `--iterate`, `--review {findings}`): the form of every CLI, easy to type, and `--` is rare in a sentence, so the request stays apart. A two-word name takes a hyphen. The old ` — {name}` is read the same, so Selo Ops' prompts and older sessions still work; the skills write `--{name}`. The rules' new **Arguments** says it once.
- **Subcommands**: plain words after the command, as `/doctor` does and as `setup` and `review` already did. `run` follows: `/selo:run web demo`, `/selo:run stop`.
- **`pilot`'s hint on one line**: the six options wrapped onto a second line. It keeps the target and the options most used, `--autonomous` first, and ends with `…`; the others stay in its description.
- The skills, the rules, the cheat sheet, the manifest doc and the stack templates' `/selo:run … demo` follow. A project picks the templates up with `/selo:setup update`.

## 2026-10-27 — selo 2.10.0: SQL Server, an option of the `angular-dotnet` pack

The person (2026-10-27): a project on `angular-dotnet` should be able to use SQL Server instead of SQLite, on the SQL Server instance installed on the developer's Windows machine, with Windows authentication. 2.9.0 chose SQLite so every test runs in process with no server; a project whose production runs on SQL Server had to swap the provider and regenerate the migrations itself.

- **Pack options.** A pack may offer a choice inside its stack: a `## Options` section (each option, its values, its default, how a component's `CLAUDE.md` shows the value taken) and, per non-default value, a folder `options/{option}/{value}/` holding only the files it replaces, at the pack's paths. One pack, not a copy: the variant can differ only in those files. `setup` asks the options with the placeholders (round 2, item 8) and lays the folder over the pack wherever it reads a pack file (full setup, `setup stack`, `setup update`); the option is read back from the component's `CLAUDE.md`, not written to the manifest. `tests/stacks.test.mjs` checks that every file of an option replaces one of its pack and that the README documents it.
- **`angular-dotnet`, `database: sqlserver`** (default `sqlite`): the SqlServer provider, the connection strings on `{{sql_server}}` (new placeholder, `localhost` recommended) with `Trusted_Connection`. The dev server's database `{{namespace}}`, the demo's `{{namespace}}_Demo`, dropped and seeded again at each start (it holds its seed alone, as the in-memory one did); a slot n > 0 suffixes both with `_Slot{n}`, since two worktrees' runs share one instance and two demos would otherwise drop each other's database. Each test class creates `{{namespace}}_Test_{guid}`, empties its tables before each test (constraints off, `DELETE`, checked again) and drops it at the end: the tests stay inside `test`. `Microsoft.Data.SqlClient` pulls a `System.Security.Cryptography.Pkcs` with known vulnerabilities and warnings are errors, so the option pins 10.0.14 transitively. Proved green from a filled copy on a local instance: build, tests (a reset across a foreign key included), lint, handoff, the demo on slot 2 started twice, no database left behind.
- The api template's SQL Server copy, the pack's `README.md` (Options, database, tests, placeholders), `ef-migrations` (engine-neutral, with SQL Server's review points) and `stacks/README.md` follow.

## 2026-10-24 — selo 2.4.0: mockup first, and the iterate mode of the fastlane

Two ideas of the person (2026-10-24): see a change before it is coded, and try changes one by one on the running app without a commit at each one. Both need the person; neither runs under autopilot.

- **`/selo:mockup {request}`**, a new skill: one static, self-contained HTML file under `.planning/mockups/`, drawn with the front's skin (its `tokens.css`, `recipes.css` and the component's `overrides.css` inlined, so it renders alike in the browser pane, as an Artifact or opened alone), one plate per state and width, iterated with targeted edits until the person validates it; the HTML is the mockup, no PNG: `try` screenshots its plates itself. Shown as an Artifact when the session can publish one (visible from the phone), else in the browser pane. Never code, never a spec, never a commit: `build` and `try` already compared a page with a blueprint's `## Mockup`, so the lane that builds the change takes ` — mockup {file}` (`fastlane` and `blueprint`), commits the file with its work, and its browser test compares the page with it (`try` step 6 now screenshots an HTML mockup's plates).
- **`/selo:fastlane {request} — iterate`**, a mode, not a lane: a fastlane's steps 1 to 6 already were the work, so the loop reuses them and defers the end. On the base branch it asks first whether to move to a worktree (uncommitted files held for long make the other sessions of the shared checkout wait). - **One folder, with or without a plan.** A section of the plan would have missed most sessions: the default path has no plan, and a past plan is never edited. One file per session, not one shared list, so two branches never collide on its last line.
- **Recorded now, applied later.** The retro applies nothing: one session is one data point, and a rule written from it alone may be wrong. `/factory:retro apply` takes the open lessons of every retro, groups the duplicates, proposes each change on the person's yes and records its status. A lesson for the factory is never applied in a project, whose plugin runs from its cache: it becomes a proposal the person carries here, `forwarded`.
- **Offered, never forced.** `/factory:retro` is the last next prompt of every step (the rule is in the workflow rules' `## Next prompts`), and `autopilot` gives it in its report; no hook runs it in the background, whose untriaged candidates pile up. Projects initialised earlier get the `retros/` folder by updating their `.claude/rules/planning.md` from the template; `samples/todo-app` has it. Version 0.4.0.

## 2026-10-19 — Autopilot: one command to developed code

- **`autopilot` chains the workflow with no click.** Every step was interactive (the grill's rounds, the spec's and the plan's yes, one stage per session with its questions), so a feature took a person at the keyboard from the spec to the last stage. The person wanted to launch one command and come back to a finished branch. Separate sessions cannot chain themselves in the desktop app, so the chain is made of fresh-context subagents in one session (CLI, desktop and cloud alike): the spec, the plan, each stage, the final review, each on its role's model, each committed before the next starts. It starts from a request, a slug with a spec or a plan folder (resumed at its Progress), stops early on ` — until spec` / ` — until plan`, and tests in the browser only with ` — with browser test`.
- **Autonomous mode of the skills.** `write-spec`, `write-plan`, `grill-me` and `implement` take a ` — autonomous` marker, sent only by `autopilot`: no question, every `grill-me` question answered with its recommendation (now mandatory, or an explicit `no recommendation possible` with the reason, which stops the pipeline with nothing written), every default taken, and a `## Decisions taken autonomously` section in the spec and the plan as the person's record. The hard rules hold: never push, integration tests `[-]`, the squash proposed as a prompt and never run, stage commits with the Progress subject. The rule is in the workflow rules (`## Autonomous mode`), and the subagent rule now allows a subagent that has the Agent tool to spawn `reviewer` and `runner`.
- **Prerequisite.** The session must run in the `auto` or `acceptEdits` permission mode with the components' commands allowed, else the subagents stall on their first prompt; the skill says so before its first step.

## 2026-10-19 — The spec opens the feature branch

## 2026-10-19 — Plan finalized replaces the branch close

The person wanted the end of a plan to be automatic and named after the plan, not the branch. ## 2026-10-16 — Founding rules

Brought from the tooling of one .NET / Angular project, where each of them was learnt the hard way.

- **Never push.** An agent that pushes publishes a mistake before a human saw it; a human pushes.
- **One stage per session.** A stage spanning two components in one session ran out of context mid-way and lost track; a fresh session resumes from the plan's Progress ticks and the branch's commits.
- **Review before every stage commit**, by a read-only agent with no stake in the code: the author of a change does not see what it misses.
- **Silence is not approval.** A spec or plan committed on an unanswered summary was reworked twice; it is committed only after an explicit yes.
- **Mechanical work goes to `runner`.** Build, test and lint output floods the lead's context and buries the decision it has to make; a hook denied those commands in the lead session, and the lead read a short report. (Hook dropped the same day, see above; the advice stays.)
- **Exploration bursts are capped.** A lead reading twenty files in a row drifted from the task; past a few calls a hook sent the search to a cheap subagent. (Dropped the same day, see above.)
- **Integration tests never run unasked.** They hit real systems (databases, containers, external services) and take minutes; the person names them when they want them.
- **The spec has one writer** (`write-spec`). Specs edited from a plan or from code drifted from the business meaning; every delta goes through the skill and ships with the change that motivated it.
- **Model guard.** A plan written on the implementer's model was shallower than one written on the planner's; each skill checked the session's model against its role and delegated when it did not fit. (Dropped the same day, see above; the preset still says which model each role is meant for.)
- **Caveman voice between agents**, normal prose for the person: tokens between agents are cost without a reader.
- **Stack-agnostic skills.** The words of a stack live in `stacks/` packs and in the components' `CLAUDE.md`, never in the skills, so the same workflow runs on the next project without porting.
