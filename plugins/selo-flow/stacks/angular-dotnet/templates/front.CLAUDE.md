## Structure

Standalone components and signals, Tailwind for layout; one folder per feature:

```
src/
  main.ts                   bootstraps App with app.config.ts
  styles.css                the theme imports first (fonts, skin, base, overrides), then Tailwind, its theme mapped to the skin's tokens
  app/
    app.ts                  the root component: <router-outlet />
    app.config.ts           router, HttpClient, the API's root url (`/api`), the translations
    app.routes.ts           one lazy entry per feature (loadChildren)
    messages-loader.ts      bundles src/i18n/messages.json for ngx-translate
  api/                      generated by `prepare` from the API's OpenAPI document (ng-openapi-gen): never edited by hand
  i18n/messages.json        every user-facing string, by key
  theme/                    fonts.css and skin.css, both written by setup: never edited; base.css (the page), overrides.css (this application's values)
  features/
    core/                   cross-cutting code, same layout as a feature
      ui/                   the shared components, one file per element of the skin's recipes; labels are inputs, no feature word
                            Panel (app-panel), PageTitle (h1[appPageTitle]), Field (app-field: label, error, the projected control),
                            Control (input[appControl], select[appControl]), SearchInput (app-search-input), Select (app-select: the chevron),
                            Button (button[appButton], variant: primary, danger, quiet, ghost), Switch (app-switch), Checkbox (input[appCheckbox]),
                            List (ul[appList], li[appListItem] with isDone, [appListItemText]), Badge, EmptyState, LoadingState,
                            ErrorMessage (role="alert"), ConfirmDialog (a native <dialog>), icons.ts (app-search-icon, app-trash-icon)
      utils/                resource-state.ts (resourceState, resourceStateWithParams), problem-details.ts (problemOf)
    {feature}/
      {feature}.routes.ts   the feature's routes, lazy-loaded by app.routes.ts
      containers/           routed pages ({name}.page.ts) and smart containers
      data-access/          {feature}.store.ts
      ui/                   dumb components and forms ({name}.form.ts)
      interfaces/           models shared by several files of the feature
      utils/                pipes, directives, helpers
```

Create only the subfolders a feature needs, and keep the tree shallow.

## Conventions

- **TypeScript strict**, no `any` (`unknown` and narrow); files in kebab-case, classes in PascalCase with no `Component` suffix, no barrel `index.ts`. Private members with `private` or `#name`, never an `_` prefix; a writable signal with a public view: `#items = signal(...)`, `readonly items = this.#items.asReadonly()`.
- **Components:** standalone, `input()` / `output()` / `model()`, signals and `computed`, the built-in control flow (`@if`, `@for`). Templates inline, moved to a same-named `.html` past ~30 lines. Element selectors `app-{name}`, attribute selectors `app{Name}`.
- **Dependencies:** a feature never imports from another feature; any feature imports from `core`; `core` imports from no feature. Something reused by one feature goes to its `ui/` or `utils/`, by several to `core/`.
- **Data:** one store per stateful feature, `data-access/{feature}.store.ts`, `@Injectable({ providedIn: 'root' })` unless the feature needs a scoped one. State at the class root (signals, `computed`, one `resourceState` / `resourceStateWithParams` slice per async value, named after its data); side effects in one `readonly actions = { … }` object of arrow functions, one per user intent. The store injects `Api` from `src/api` and calls `this.api.invoke(getOrders, params)`: no hand-written API service. Pages inject the store; dumb components never do.
- **Types** of requests and responses come from `src/api/models`, never redeclared by hand.
- **Pages** are routed (`containers/{name}.page.ts`), read the store and compose dumb components; **dumb components** (`ui/`) talk only through inputs and outputs and inject nothing but pure utilities (`TranslateService`).
- **Forms:** Signal Forms (`@angular/forms/signals`), one dumb `{name}.form.ts` per form in `ui/`: its schema and model are `#private`, `fields` is protected, it binds the shared controls with `[formField]`, shows an error only once the field is `dirty()` or `touched()`, takes `isSaving` (and `detail` to edit), emits `save` with the value; the page calls the store. A `400`'s field errors (`problemOf(error)?.errors`) map to field messages. No template-driven or classic reactive forms.
- **i18n:** every user-facing string goes through ngx-translate (`{{ 'orders.list.empty' | translate }}`); keys live in `src/i18n/messages.json`, nested `{feature}.{element}.{text}`, added in the same change; a missing key is a review finding.
- **Styling:** each component styles itself (`styles` in the decorator) from the skin's variables only: no literal color, radius, shadow, font family or control height (see Design). Tailwind lays out (`flex`, `grid`, `gap-*`, `p-*`); its colors, radii, fonts and shadows are the skin's (`bg-surface`, `text-muted`, `rounded-card`), its default palette is off. No `::ng-deep`.
- **Loading and errors:** every page that reads data shows a loading state and an error state; a failed mutation shows the problem details' message.

## Design

The skin named in the `component` block above: its fonts in `src/theme/fonts.css` and its tokens in `src/theme/skin.css` (both written by setup, rewritten by `/selo-flow:setup skin`), imported first by `src/styles.css`, then `base.css` and `overrides.css`. The UI follows the selo plugin's design rules (`reference/ui-design.md`), its element recipes (`skins/recipes.css`) and the skin's `SKIN.md`, read in place; this section wins over them. Features compose the `features/core/ui` components and style only their own layout; a recipe or a component two features need that `core/ui` lacks is added there, in the same way.

- Variables this application changes: in `src/theme/overrides.css`, never in `skin.css`.
- Rules this application adds or replaces: here, one line each.

## Local run

- Prerequisites: Node {{node_version}}, `npm ci`.
- Run: `/selo-flow:run` starts the API, then the front, on this worktree's slot (http://localhost:{{port}} on slot 0, the port + 10 per slot); `npm run app` at the root does the same outside a session. `npm run dev` alone serves http://localhost:{{port}} and expects the API on http://localhost:{{api_port}}.
- Demo: `npm run demo` → http://localhost:{{demo_port}} (slot 0; `/selo-flow:run demo` on this worktree's slot), proxied to the API's demo on port {{api_demo_port}}. `try` starts both demos and stops them after the test.
- `prepare` regenerates `src/api/` from the API's committed handoff file; run it at the start of every front stage.
