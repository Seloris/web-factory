Full TypeScript: Express API (zod, Drizzle ORM on PostgreSQL, PGlite in-process for local runs and tests, Vitest + Supertest) and React front (Vite, TanStack Query, client typed from the API's OpenAPI document).

# react-express

Two component templates and three skills, TypeScript end to end, Node 22 or later.

| File | For |
|---|---|
| `templates/api.CLAUDE.md` | kind `api`: Express 5, one folder per feature (`schema` → `repository` → `service` → `routes`), zod for every input and output, Drizzle ORM on PostgreSQL, problem details for errors, OpenAPI document generated from the zod contracts; tests with Vitest and Supertest against an in-memory PGlite database. |
| `templates/front.CLAUDE.md` | kind `front`: React with Vite, React Router, TanStack Query, `openapi-fetch` over types generated by `openapi-typescript` from the API's handoff file. |
| `gitignore` | lines `setup` appends to the project's `.gitignore`: `node_modules/`, `dist/`, the PGlite data folder. |
| `skills/drizzle-migrations` | generate, check, apply and reset Drizzle migrations, from the `## Database` table of the api component's `CLAUDE.md`. |
| `skills/openapi-client` | export the OpenAPI document from the zod contracts without running a server (`handoff`) and regenerate the front's types (`prepare`). |
| `skills/write-api-tests` | derive a route's test matrix from its contract, guard, zod schemas and service, and write it with Vitest + Supertest, from the `## API tests` table of the api component's `CLAUDE.md`. |
| `skeleton/api`, `skeleton/front` | the code each component starts from, copied by `setup` into an empty component folder (see below). |

## Skeleton

The minimum for which every command the templates declare passes with zero features. `setup` copies `skeleton/{kind}/` into the component's path when that path holds nothing but its `CLAUDE.md`, fills the placeholders (`{{name}}`, `{{node_version}}`, `{{api_url}}`), then runs **`npm install`** from the component's path (a front then gets its skin's tokens and fonts, see Skin below), and checks that the component's `build` and `test` commands are green before committing. Dependency versions are pinned; `npm install` writes the lock file the project commits, and `npm ci` is the setup from then on.

- **api**: `src/app.ts`, `server.ts`, `config.ts`; `db/schema.ts` and `db/client.ts` on PGlite; `shared/errors.ts` (the `AppError`s and the problem-details middleware), `validate.ts`, `clock.ts`, `openapi.ts` (the registry); `scripts/export-openapi.ts`; `test/setup.ts`, `test/factories.ts` and `test/shared/errors.test.ts` (a body that is not valid JSON gets a `400`); `drizzle.config.ts`, an empty migrations journal, `.data/.gitkeep` (PGlite needs the parent folder); Vitest, eslint flat config, strict tsconfig. One route, `GET /health`, in `features/health/` with its Supertest test: it proves the chain (app, clock, test context, OpenAPI registration) and is the first reference test. `src/demo.ts` and an empty `src/seed/demo.ts` give `npm run demo`: the app on an in-memory PGlite, migrated and seeded at each start, on `{{api_demo_port}}`.
- **front**: Vite with the React plugin and the `/api` proxy, `src/main.tsx` (the theme imports first, then QueryClientProvider, RouterProvider), `src/router.tsx` (one route), `src/api/client.ts` (`openapi-fetch`) and an empty but valid `src/api/schema.d.ts`, so `build` is green before the first `handoff` / `prepare`; `src/shared/ui/theme/base.css`, an empty `overrides.css` and an empty `fonts.ts` (the skin's `skin.css` and its font imports come from the skin, below); the shared components of `src/shared/ui/` (below); eslint flat config with the React hooks rules, strict tsconfig; `npm run demo` serves it in the `demo` mode on `{{demo_port}}`, its `/api` proxy on the API's demo, with `--force`.

## Skin

A front component of this pack has a `skin` (the selo plugin's `skins/`). `setup` copies the skin's `tokens.css` to **`src/shared/ui/theme/skin.css`**, and creates `src/shared/ui/theme/overrides.css` when absent (an existing one is never touched). `src/main.tsx` imports, before anything else, `fonts.ts`, then `skin.css`, then `base.css`, then `overrides.css`, so every component style comes after them.

### Shared components

The skeleton ports the plugin's `skins/recipes.css` into `src/shared/ui/`: one `{Name}.tsx` per element, a named export with its `{Name}.module.css`, reading the token contract only, the recipe's class names in camelCase (`select-wrap` is `selectWrap`). No user-facing string of their own (every label is a prop, for the i18n layer), no feature word, and no `className` prop: a feature lays them out through a wrapper of its own and styles only that layout.

| Component | Recipe | Notes |
|---|---|---|
| `Panel.tsx` | panel | `Panel({ children })`: the page's surface, 680px at most, centred |
| `PageTitle.tsx` | headings | `PageTitle({ children })`: the page's `h1` |
| `Field.tsx` | field | `Field({ label, error, children })`, `error: string \| null`, `children(control: FieldControl)`: the control is a render prop that spreads `control` (`id`, `aria-invalid`, `aria-describedby`); the label's `htmlFor` and the error's id come from `useId` |
| `TextInput.tsx` | input | the input's props, `className` aside |
| `SearchInput.tsx` | search | `type="search"` with the `SearchIcon`; the native clear button hidden |
| `Select.tsx` | select | the native select, its chevron drawn by the wrapper |
| `Button.tsx` | buttons | `variant`: `primary`, `danger`, `quiet` (default) or `ghost` (a row action, an icon before its text); `type="button"` unless given |
| `Switch.tsx` | switch | `Switch({ label, checked, disabled, onChange(checked) })`: a checkbox with `role="switch"` |
| `Checkbox.tsx` | checkbox | the input's props, `type` and `className` aside; a disabled look the recipe lacks |
| `List.tsx` | list | `List`, `ListItem({ isDone })` and `ListItemText`, the part `isDone` strikes through, in one module |
| `Badge.tsx` | badge | |
| `EmptyState.tsx` | empty | a list with no row: empty, or filtered to nothing |
| `LoadingState.tsx` | | `role="status"`: the empty state's box without its border, while a list loads |
| `ErrorMessage.tsx` | error | `role="alert"`; a failed load composes it with a retry `Button` |
| `ConfirmDialog.tsx` | dialog | a native `<dialog>` opened with `showModal()`: `isOpen`, `title`, `message`, both labels, `isPending`, `error`, `onConfirm`, `onCancel` (also on Escape, never while pending) |
| `icons.tsx` | | `SearchIcon`, `TrashIcon`: 16px, strokes in `currentColor`, `aria-hidden`, always beside text |

A project adds a shared component the same way (a recipe the skeleton lacks, a component two features need), and changes one in place: they are the project's code from the first commit.

### Fonts

Self-hosted from npm with [Fontsource](https://fontsource.org): no request to a font CDN, versions pinned with the rest. `setup` takes the skin's row below, writes its import lines into **`src/shared/ui/theme/fonts.ts`** (which it owns: never edited by hand, rewritten when the skin changes), and runs `npm install --save-exact {packages}` from the component's path after the skeleton's `npm install`. Switching skins runs `npm uninstall` on the previous row's packages first. Static packages only: the variable ones register `'{Face} Variable'`, which the tokens' `font-family` does not name. The weights are those of the skin's `SKIN.md`, a range taken as every hundred in it; each import ships its own `@font-face` with `font-display: swap`.

| Skin | Packages (pinned) | `fonts.ts` imports |
|---|---|---|
| `modern` | `@fontsource/geist@5.3.0` | `geist/400.css`, `geist/500.css`, `geist/600.css`, `geist/700.css` |
| `editorial` | `@fontsource/fraunces@5.3.0`, `@fontsource/newsreader@5.3.0` | `fraunces/400.css`, `fraunces/500.css`, `fraunces/600.css`, `fraunces/400-italic.css`, `fraunces/500-italic.css`, `fraunces/600-italic.css`, `newsreader/400.css`, `newsreader/500.css` |
| `brutalist` | `@fontsource/archivo-black@5.3.0`, `@fontsource/ibm-plex-mono@5.3.0` | `archivo-black/400.css`, `ibm-plex-mono/400.css`, `ibm-plex-mono/600.css` |
| `aurora` | `@fontsource/outfit@5.3.0` | `outfit/400.css`, `outfit/500.css`, `outfit/600.css` |
| `swiss` | `@fontsource/schibsted-grotesk@5.3.0` | `schibsted-grotesk/400.css`, `schibsted-grotesk/500.css`, `schibsted-grotesk/700.css`, `schibsted-grotesk/800.css` |
| `soft` | `@fontsource/nunito@5.3.0` | `nunito/400.css`, `nunito/600.css`, `nunito/700.css`, `nunito/800.css` |

Each import is written `import "@fontsource/{path}";`, in the table's order, under a first comment line naming the skin. Editorial's Fraunces loses its optical sizes in the static files; a project that wants them installs `@fontsource-variable/fraunces` and sets `--font-display: 'Fraunces Variable', …` in its `overrides.css`. A new skin adds its row here in the same change.

## The database

PostgreSQL, through Drizzle ORM. Locally and in tests it runs as **PGlite**: PostgreSQL compiled to WebAssembly, an npm package that runs inside the Node process. No Docker, no server to install, no native build: `npm ci` is the whole setup, on Windows as elsewhere.

- **Local run**: PGlite persisted in a git-ignored folder (`.data/pglite`); deleting the folder and re-applying the migrations resets it.
- **Tests**: one in-memory PGlite per test file, migrated once (`beforeAll`), its tables truncated between tests; nothing survives the run.
- **Deployment**: a real PostgreSQL through `drizzle-orm/node-postgres`, with the same schema and the same migrations. Only the driver line of `src/db/client.ts` changes.

Why not SQLite: its Node drivers either need a native addon (prebuilt binaries lag behind new Node versions, and Windows then needs build tools) or depend on the Node version (`node:sqlite`); and a project that later moves to PostgreSQL rewrites its migrations. PGlite is the real PostgreSQL dialect from the first commit.

## Tests

The API's route tests run in-process against in-memory PGlite: they touch no external system and take seconds, so they are part of the api component's `test` command and run in full at the end of every stage. The pack therefore declares no `integration_tests` command. A project that adds tests against real external systems (a hosted database, a third-party API) puts them behind `integration_tests`, which never runs unasked.

The front has no unit tests of its components, as in the workflow's default: the `try` skill checks a change on the demo. Its pure `.ts` modules (no React, no DOM) may have Vitest tests: the project adds Vitest and `test: npx vitest run` to its front component, and every front stage then gains a test step.

The demo (`commands.demo`, `demo_url` in both component blocks) is what `try` runs on by default: seeded data, its own ports, started in the background and stopped after the test, so the developer's servers and local database are never touched.

## Placeholders

The templates' `{{placeholders}}` are asked by `setup` (round 2, after the common ones: `{{name}}`, `{{description}}`, `{{url}}`, `{{logins}}`, `{{skin}}`), with these recommended values. An optional one left empty drops its line.

| Placeholder | Template | Recommended | Meaning |
|---|---|---|---|
| `{{handoff_file}}` | api | `openapi.json` | the API's OpenAPI document, relative to the api component |
| `{{api_handoff}}` | front | `../api/openapi.json` | the same file seen from the front component |
| `{{api_url}}` | api, front | `http://localhost:3000` | where the API listens locally (the front's `/api` proxy target) |
| `{{node_version}}` | api, front | `22` | the Node major version |
| `{{reference_tests}}` | api | `test/health/health.routes.test.ts` | the test files `write-api-tests` imitates: the skeleton's health route test until the project has richer ones |
| `{{authenticated_calls}}` | api | `` `seed.user({ roles })` then `.set(authHeader(user))` `` when the application has a sign-in; empty otherwise (optional) | how a route test authenticates |
| `{{i18n_file}}` | front | `src/shared/lib/i18n/{lang}.json` | where the translation keys live |
| `{{styling}}` | front | `CSS Modules` | the styling approach |
| `{{api_demo_port}}` | api, front | `3101` | the port of the API's demo (`npm run demo`), apart from the dev server's |
| `{{demo_port}}` | front | `5181` | the port of the front's demo, the component's `demo_url` |
| `{{local_dependencies}}` | api | empty (optional) | what else must run locally (a third-party API, a queue…) |

Conventions worth keeping when the templates are adapted: time through an injected `Clock`, never `new Date()` or `Date.now()` in services; booleans with the `is`/`has`/`can` prefix; one zod schema per input and output, the TypeScript types inferred from it (`z.infer`), never declared twice; errors as typed `AppError`s mapped to problem details by one middleware, never a bare `throw new Error`; no hand-edited migration; every write route's test asserts the database state.
