.NET 10 API in Clean Architecture (Minimal APIs, FluentValidation, EF Core on SQLite, xUnit v3 in process) and one Angular front (standalone and signals, Tailwind, Signal Forms, ngx-translate, client generated by ng-openapi-gen from the API's OpenAPI document).

# angular-dotnet

Two component templates and three skills: a .NET API and a single Angular front (a front office; a project that later needs a back office adds a second front component the same way). The conventions come from a production Angular/.NET project, made simpler: no mediator library (handlers injected into Minimal API endpoints), no repository, SQLite instead of SQL Server, so every test runs in process with no Docker.

| File | For |
|---|---|
| `templates/api.CLAUDE.md` | kind `api`: .NET 10, four projects (`Domain` ← `Application` ← `Infrastructure` / `Api`), one folder per feature in each, a use case per file (`Command`, `Validator`, `Handler` nested), Minimal API endpoints, FluentValidation behind an endpoint filter, problem details with a `code` for every error, `TimeProvider` for time, EF Core on SQLite, the OpenAPI document generated at build time; tests with xUnit v3 and Shouldly against `WebApplicationFactory` on an in-memory SQLite database. |
| `templates/front.CLAUDE.md` | kind `front`: Angular 22, standalone components and signals, one folder per feature (`containers/`, `data-access/` with its store, `ui/`), stores over `resourceState`, Signal Forms, ngx-translate, Tailwind mapped to the skin's tokens, the API client generated by ng-openapi-gen (`Api.invoke(getOrders)`). |
| `gitignore` | lines `setup` appends to the project's `.gitignore`: `bin/`, `obj/`, `TestResults/`, the SQLite files, `node_modules/`, `dist/`, `.angular/`. |
| `skills/ef-migrations` | add, review, apply, remove and reset EF Core migrations, from the `## Database` table of the api component's `CLAUDE.md`. |
| `skills/openapi-client` | export the OpenAPI document without serving the API (`handoff`) and regenerate the front's client (`prepare`). |
| `skills/write-api-tests` | derive an endpoint's test matrix from its route, policy, validator, handler and domain rules, and write it with xUnit v3, from the `## API tests` table of the api component's `CLAUDE.md`. |
| `skeleton/api`, `skeleton/front` | the code each component starts from, copied by `setup` into an empty component folder (see below). |

## Skeleton

The minimum for which every command the templates declare passes with zero features. `setup` copies `skeleton/{kind}/` into the component's path when that path holds nothing but its `CLAUDE.md`, fills the placeholders, then runs the install command from the component's path: **`dotnet restore` then `dotnet tool restore`** for the api, **`npm install`** for the front (which then gets its skin's tokens and fonts, see Skin below). It checks that the component's `build` and `test` commands are green before committing. Versions are pinned: NuGet versions in `Directory.Packages.props`, the SDK in `global.json`, `dotnet-ef` in `.config/dotnet-tools.json`, npm versions exact; `npm install` writes the lock file the project commits, and `npm ci` is the setup from then on.

Only the names of the Placeholders table below are placeholders, in the skeletons as in the templates. Angular's `{{ … }}` interpolation (`{{ label() }}` in the shared components, `{{ 'orders.list.empty' | translate }}` in `templates/front.CLAUDE.md`) is code, copied as it is. File and folder names hold no placeholder: the projects are `src/Domain`, `src/Application`, `src/Infrastructure`, `src/Api`, `tests/Api.Tests`, and their assemblies and namespaces are `{{namespace}}.{Project}` (`Directory.Build.props`).

- **api**: `App.slnx`, `global.json` (SDK 10, tests on Microsoft.Testing.Platform), `Directory.Build.props` (net10.0, nullable, warnings as errors), `Directory.Packages.props`; `Domain/Common/` (`DomainException` and its `NotFound`, `Forbidden`, `Conflict` subclasses); `Application/Common/IAppDbContext.cs` and `DependencyInjection.cs` (the validators and every nested `Handler`); `Infrastructure/Data/AppDbContext.cs` and `DemoSeeder.cs` (empty), `DependencyInjection.cs` (SQLite, the kept-alive connection an in-memory database needs, `TimeProvider.System`, migrations at start); `Api/Program.cs`, `Common/ProblemDetailsExceptionHandler.cs` and `ValidationFilter.cs`, `appsettings.json` and `appsettings.Demo.json`, `.data/.gitkeep`; `openapi.json`, the skeleton's handoff file, so the front's `prepare` works before the first api stage. One endpoint, `GET /health`, in `Features/Health/`, with its test: it proves the chain (host, clock, test factory, OpenAPI metadata) and is the first reference test. `tests/Api.Tests/`: `ApiFactory`, `ApiTest`, `TestTimeProvider`, and the tests of the problem details (an unknown route, each domain exception's status and code) and of the validation filter.
- **front**: `angular.json` (one project, `app`, its `serve` on `proxy.conf.mjs`), `serve.mjs` (see Ports), strict `tsconfig.json` with strict templates, `.postcssrc.json` (Tailwind), `eslint.config.mjs` (angular-eslint, the template accessibility rules); `src/main.ts`, `styles.css`, `app/app.ts` (`<router-outlet />`), `app.config.ts`, `app.routes.ts` (empty), `messages-loader.ts` and `src/i18n/messages.json` (`{}`); `src/api/`, the client generated from the skeleton's `openapi.json`; `src/theme/base.css`, an empty `overrides.css` and an empty `fonts.css` (the skin's `skin.css` and its font imports come from the skin, below); `src/features/core/ui/` (the shared components, below) and `src/features/core/utils/` (`resource-state.ts`, `problem-details.ts`).

## Routes

Where `setup` finds a front's pages (the route scan, `setup` and `setup specs`). The routes are declared in **`src/app/app.routes.ts`** of the front component, and in each feature's **`src/features/{feature}/{feature}.routes.ts`** that it lazy-loads. Each entry is read this way:

- **The route:** its `path`. An entry with `loadChildren` (a feature's routes) or `children` joins its parent's path to each of its entries (`orders` + `:id` → `/orders/:id`); `path: ''` takes its parent's path.
- **The page module:** the file of `loadComponent: () => import('./containers/{name}.page')`, or the component given to `component` and the file it is imported from. The recommended slug comes from it: `order-detail.page.ts` → `order-detail`, the page on `/` → `home`.
- **Not a page:** an entry with `loadChildren` itself (its file is read instead), an entry with no page component and `children` (a layout: the shell, `domain/app.md`), a `**` entry (not found: `app`), an entry with `redirectTo` (a redirect): the scan lists none of them as a page.

A route defined anywhere else (routes built in a loop, a second `provideRouter`) is named in the scan's report, with its file, for the person to place.

## Ports

How a run of the app (the selo plugin's `run.mjs`, behind `/selo:run`, `try` and `npm run app`) reaches the components' scripts.

- **Keys.** Each component block carries `port` (dev) and `demo_port` (demo), the base ports: a run on slot n adds 10 × n.
- **API.** `Program.cs` listens on `http://localhost:{PORT}`, `PORT` read from the configuration: the environment of a run, else `appsettings.json` (`{{api_port}}`), or `appsettings.Demo.json` (`{{api_demo_port}}`) for the demo. `dotnet run --no-launch-profile`: no `launchSettings.json`, whose urls would win. The demo runs `-c Release`: a dev API running on the same worktree locks `bin/Debug`, and a demo built there after a change would fail to copy its files. The local SQLite file (`src/Api/.data/app.db`) belongs to the worktree; the demo's database is in memory.
- **Front.** `ng serve` reads neither `PORT` nor `API_URL`, and a `package.json` script cannot expand `$PORT` with `cmd.exe`: the `dev` and `demo` scripts run **`serve.mjs`**, which starts `ng serve --port` on `PORT` (default `{{port}}`, `{{demo_port}}` with `--demo`) and sets `API_URL` when absent (the API's base port of the mode). `proxy.conf.mjs` sends `/api` to `API_URL`, the prefix stripped. A taken port fails the start.
- **`npm run app`.** `setup` writes the project's `selo-run.mjs` launcher, and this pack adds, in a `package.json` at the project's root (created with `"private": true` and nothing else when absent), the scripts `"app": "node selo-run.mjs"` and `"app:demo": "node selo-run.mjs --demo"`: `npm run app` starts every component on the worktree's slot, Ctrl+C stops them.

## Skin

A front component of this pack has a `skin` (the selo plugin's `skins/`). `setup` copies the skin's `tokens.css` to **`src/theme/skin.css`**, and creates `src/theme/overrides.css` when absent (an existing one is never touched). `src/styles.css` imports, before anything else, `fonts.css`, then `skin.css`, then `base.css`, then `overrides.css`, then Tailwind, whose `@theme` maps its colors, radii, fonts and shadows to the skin's variables and turns its default palette off; component styles come after the global stylesheet.

### Shared components

The skeleton ports the plugin's `skins/recipes.css` into `src/features/core/ui/`: one `{name}.ts` per element, a standalone component whose `styles` read the token contract only. No user-facing string of their own (every label is an input or projected content, for the i18n layer), no feature word. Components that restyle a native element use an attribute selector on it (`button[appButton]`), so the element keeps its own attributes, events and Signal Forms binding (`[formField]`); a feature lays them out through a wrapper of its own and styles only that layout.

| Component | Recipe | Notes |
|---|---|---|
| `panel.ts` | panel | `app-panel`: the page's surface, 680px at most, centred |
| `page-title.ts` | headings | `h1[appPageTitle]`: the page's `h1` |
| `field.ts` | field | `app-field` with `label` and `error` (`string \| null`), the control projected; `FieldControl`, a host directive of `Control`, gives the projected control its `id`, `aria-invalid` and `aria-describedby` |
| `control.ts` | input, select | `input[appControl]`, `select[appControl]`: the native control restyled; room for the icon inside `app-search-input`; the native search clear button hidden |
| `search-input.ts` | search | `app-search-input` around an `<input appControl type="search">`, with the `SearchIcon` |
| `select.ts` | select | `app-select` around a `<select appControl>`: draws its chevron |
| `button.ts` | buttons | `button[appButton]`, `variant`: `primary`, `danger`, `quiet` (default) or `ghost` (a row action, an icon before its text); `type="button"` unless given |
| `switch.ts` | switch | `app-switch` with `label`, `disabled` and the model `checked`: a checkbox with `role="switch"` |
| `checkbox.ts` | checkbox | `input[type=checkbox][appCheckbox]`; a disabled look the recipe lacks |
| `list.ts` | list | `ul[appList]`, `li[appListItem]` (`isDone`) and `[appListItemText]`, the part `isDone` strikes through, in one module |
| `badge.ts` | badge | `app-badge` |
| `empty-state.ts` | empty | `app-empty-state`: a list with no row, empty or filtered to nothing |
| `loading-state.ts` | | `app-loading-state`, `role="status"`: the empty state's box without its border, while a list loads |
| `error-message.ts` | error | `app-error-message`, `role="alert"`; a failed load composes it with a retry button |
| `confirm-dialog.ts` | dialog | `app-confirm-dialog`, a native `<dialog>` opened with `showModal()`: `isOpen`, `title`, `message`, both labels, `isPending`, `error`, outputs `confirmed` and `cancelled` (also on Escape, never while pending) |
| `icons.ts` | | `app-search-icon`, `app-trash-icon`: 16px, strokes in `currentColor`, `aria-hidden`, always beside text |

A project adds a shared component the same way (a recipe the skeleton lacks, a component two features need), and changes one in place: they are the project's code from the first commit.

### Fonts

Self-hosted from npm with [Fontsource](https://fontsource.org): no request to a font CDN, versions pinned with the rest. `setup` takes the skin's row below, writes its import lines into **`src/theme/fonts.css`** (which it owns: never edited by hand, rewritten when the skin changes), under its comment, and runs `npm install --save-exact {packages}` from the component's path after the skeleton's `npm install`. Switching skins runs `npm uninstall` on the previous row's packages first. Static packages only: the variable ones register `'{Face} Variable'`, which the tokens' `font-family` does not name. The weights are those of the skin's `SKIN.md`, a range taken as every hundred in it; each import ships its own `@font-face` with `font-display: swap`.

Each import is written `@import "@fontsource/{path}";`, in the table's order, under a first comment line naming the skin. Editorial's Fraunces loses its optical sizes in the static files; a project that wants them installs `@fontsource-variable/fraunces` and sets `--font-display: 'Fraunces Variable', …` in its `overrides.css`. A new skin adds its row here in the same change.

## The database

SQLite through EF Core, with the same migrations everywhere. Microsoft.Data.Sqlite ships its native library in the NuGet package: `dotnet restore` is the whole setup, on Windows as elsewhere, with no server and no Docker.

- **Local run**: a file, `src/Api/.data/app.db` (git-ignored), created and migrated at the API's start; deleting it resets the database.
- **Demo and tests**: an in-memory database (`Mode=Memory;Cache=Shared`), kept alive by one open connection for the app's lifetime, migrated at start; each test class has its own, its tables emptied before each test.
- **Deployment**: SQLite on a persistent volume, through `ConnectionStrings__Default`. A project that outgrows it moves to SQL Server or PostgreSQL: the EF provider line of `Infrastructure/DependencyInjection.cs` changes, and the migrations are generated again for the new provider (a blueprint's work).

## Tests

The API's endpoint tests run in process against in-memory SQLite: they touch no external system and take seconds, so they are part of the api component's `test` command and run in full at the end of every stage. The pack therefore declares no `integration_tests` command. A project that adds tests against real external systems (a hosted database, a third-party API) puts them in a separate test project behind `integration_tests`, which never runs unasked.

The front has no unit tests, as in the workflow's default: the `try` skill checks a change on the demo.

The demo (`commands.demo`, `demo_port` in both component blocks) is what `try` runs on by default: seeded data, its own ports, started in the background and stopped after the test, so the developer's servers and local database are never touched.

## Placeholders

The templates' and skeletons' `{{placeholders}}` are asked by `setup` (round 2, after the common ones: `{{name}}`, `{{description}}`, `{{logins}}`, `{{skin}}`), with these recommended values. An optional one left empty drops its line.

| Placeholder | Where | Recommended | Meaning |
|---|---|---|---|
| `{{namespace}}` | api | the project's name in PascalCase (`todo-app` → `TodoApp`) | the root namespace and assembly prefix of the .NET projects |
| `{{api_handoff}}` | front | `../api/openapi.json` | the API's handoff file seen from the front component (the api writes it at its root) |
| `{{api_port}}` | api, front | `5080` | the API's dev port, the api component's `port` (the front's proxy target without `API_URL`) |
| `{{port}}` | front | `4200` | the front's dev port, the component's `port` |
| `{{api_demo_port}}` | api, front | `5180` | the port of the API's demo, the api component's `demo_port` |
| `{{demo_port}}` | front | `4280` | the port of the front's demo, the component's `demo_port` |
| `{{node_version}}` | front | `24` | the Node major version (Angular 22: `^22.22.3`, `^24.15.0` or `>=26`) |
| `{{ui_lang}}` | front | the application's language, as a BCP 47 code (`fr`) | the `lang` of the page and the translation language |
| `{{reference_tests}}` | api | `tests/Api.Tests/Health/HealthEndpointsTests.cs` | the test files `write-api-tests` imitates: the skeleton's health test until the project has richer ones |
| `{{authenticated_calls}}` | api | how a test signs in when the application has a sign-in (a client from `Api.CreateClient()` with the user's token); empty otherwise (optional) | how an endpoint test authenticates |
| `{{local_dependencies}}` | api | empty (optional) | what else must run locally (a third-party API, a queue…) |

Conventions worth keeping when the templates are adapted: time through the injected `TimeProvider`, never `DateTime.UtcNow`; booleans with the `Is`/`Has`/`Can` prefix; a use case's validator for format, its handler and the domain for rules, never both; errors as domain exceptions with a stable code, mapped to problem details in one place; no hand-edited migration; every write endpoint's test asserts the database state; the front calls the API only through the generated `Api` from a store.
