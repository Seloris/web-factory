# Changelog

Why each behaviour of the board exists. A behaviour changes with the case that motivated it; the entry says which. Newest first. The entries before 1.0.0 were written in the factory's CHANGELOG, under the board's own version numbers.

## 2026-10-21 — selo-flow-board 1.0.0: the board of selo-flow

- **Renamed** `selo-flow-board`, reading `selo-flow.yaml` and the `/selo-flow:` prompts; its export moves to `~/.claude/selo-flow-board/`.
- **No branches, no squash.** The review checkbox, ` — with review`, the `Squasher` button, the ` — close the branch` prompts and the branch's commit count (`aheadCount`, `branchFeature`) are gone with them; the review step prepares `/selo-flow:review {plan folder}`. Every session commits on the shared base branch, so a stage's SHA is now looked up in the last 2000 commits instead of 200: on a busy `develop`, older stages showed as not committed.
- **Areas.** An area with a spec and no plan has no next action (the board would otherwise offer `write-plan` for every three-line area); `+ Nouveau plan` still starts one. The spec's `Status` is no longer read: the timeline says `présente` or `absente`. `review {slug}` lands on the spec row.
- **The fastlane is followed.** `/selo-flow:implement {request}` named no feature, so the board recorded no run: a typed fastlane showed nothing, and an autopilot whose subagent ran it ended `arrêté · à reprendre` with no resume button. `implement` now takes a free request like `write-spec` and `autopilot`, named at its first commit. A `review` with a bare argument records a run only when it names an area the board knows: `review HEAD` showed as a session on a feature `HEAD`.
- **The demo test is the default.** The autopilot's checkbox reads `☐ Sans test navigateur` and adds ` — without browser test`.
- **The export is `schemaVersion: 3`:** `aheadCount`, `squash`, `markers.review` and the features' `specStatus` are gone; the companion app reads the new shape. The `advisor` role left the presets' copy. Version 1.0.0.

## 2026-10-20 — The board sets the models and its filters add up

- **The roles' models from the board.** Changing a role's model meant editing `factory.yaml`'s `models` by hand, in the shape `factory-init` writes. The person wanted a configuration screen. The board's `⚙ Modèles` lists the six roles with their model and writes the map the way `factory-init` does (only the roles off the `standard` preset), left uncommitted.
- **Filters that add up.** A filter chip kept only its features, so the person could not see two features in progress and a finalized one at once. The chips now add up (a press adds, a second press removes, `features` clears), a `plan prêt` chip covers the one state no chip reached, and the folded finalized line shows them beside the others. Version 0.9.0.

## 2026-10-20 — The board drives and follows the autopilot

- **One run for the pipeline.** `/factory:autopilot` was a `/factory:` prompt the board did not know: its run landed on one step and stayed `en cours` through the whole pipeline (the orchestrator never commits), while each subagent's run showed under its step with `cette session`, so the band of that session named the subagent at work, offered the plan's next step between two subagents, and the live list showed two lines of the same session. The board now records the `autopilot` run as the pipeline: `Autopilot · {step}`, its step moved at each subagent spawned with a `/factory:` brief, the feature and the plan folder taken from them, and its end read from its main loop's turn (the pipeline runs in one turn): `done` when the last subagent committed, `interrupted` (`arrêté · à reprendre`) otherwise, its subagents left waiting interrupted with it. The session list shows the pipeline only; each step row keeps its subagent's run; the band offers `Reprendre l'autopilot` after a stop.
- **A free request has no slug yet.** `write-spec` and `autopilot` from a request (`add tags to the todos`) recorded a run on the request's first word as a slug (`add`). A bare slug is now one token, alone or before an option; a request records a run without a feature (`nouvelle feature`), named at the spec's commit from its scope (`docs({slug}): spec`).
- **The autopilot is launched from the board.** Each card with a spec gets `⚡ Autopilot` under its framed step (`/factory:autopilot {plan folder | slug}`, with `☐ Test navigateur` for ` — with browser test`), the header `⚡ Nouvelle feature` (`/factory:autopilot ` to complete with the request), and a card an autopilot works on shows the `⚡ autopilot · {step}` pill and offers no other prompt. Version 0.8.0.

## 2026-10-19 — The board follows sessions driven by a brief

- **A skill called through the `Skill` tool records a run.** A session started by another session with a prose brief ran `/factory:write-plan` then `/factory:implement … — stages 1-2 (api, web), chained — with review` through the `Skill` tool, never from a typed prompt, and the board showed nothing running: it only listened to `prompt.submit`. The board now hooks the `Skill` tool call too (`factory:write-spec`, `factory:write-plan`, `factory:implement`, `factory:review`, with or without the prefix, main loop only) and records the same run from the same text.
- **A `/factory:` brief given to a subagent records a run.** A session orchestrating a plan by hand (the harness refused to start a session from an event-driven turn) handed the api stage to a subagent through the `Agent` tool, with the `/factory:implement … — stage 1 (api) — with review` prompt in its brief; the board ignored every event carrying an `agentId`, so the stage showed its ticks but never a session on it, and the subagent's commit closed nothing. The board now hooks `agent.spawn` from the main loop: a brief whose first `/factory:` line names a feature records a run carrying the subagent's id, and the turns, the commit and the end of that loop move that run, as the main loop's move its own. A spawn from inside a subagent records nothing.
- **Runs are matched by repository, not by root.** That session ran in a git worktree of the project, so its run's root was the worktree path and a board opened at the main checkout never listed it. A run now carries the repository's git common dir (`git rev-parse --git-common-dir`, absolute), read once per refresh, and the board lists the runs whose common dir is its own; a record written before the field existed is still matched on its root. The plan folder lives on the worktree's branch, so the main checkout may not have the feature's row: such a run is listed with the live sessions only, as a run of an unknown feature already was.
