# selo-flow-board

A Claude Code mod (function hooks) for projects that use selo-flow. It opens a pane headed by one line: the project, the branch and its uncommitted files as pills, a `⚡ Nouvelle feature` button (the autopilot of a feature that does not exist yet: it fills `/selo-flow:autopilot ` and the person types the request after it), `⟳`, and `⚙ Modèles`, which swaps the features for the configuration screen (`← Features` brings them back). Under it, a row of filter chips (features, en cours, à valider, plan prêt, sans plan, finalisées); they add up: a press adds its features to those shown, a second press takes them away, `features` clears them all and shows every feature and the count of the stages left. Then the live sessions, one line each (its status glyph, the feature, its step and that step's count, a status pill with its duration, the session; a click unfolds its feature on that plan). Then the features, grouped by state (En cours, À valider, Plan prêt, Spec seule, Sans spec), one card each framed in the colour of its state: its slug, a state pill, an `⚡ autopilot · {step}` pill while an autopilot works on it, one segment per stage (green done, orange the one at hand; `█▓░` on the terminal) with the count, the button that prepares the next `/selo-flow:` prompt (none while an autopilot works on the feature), and its title under them when it differs from the slug. The finalized features are folded on one line at the bottom (`▸ N feature(s) finalisée(s) · slugs`); a press shows them with the others (every chip on, or `finalisées` added to the chips pressed), as the `finalisées` chip does, and so does unfolding one of them (an older plan picked). A card unfolds into the vertical timeline of its spec and of the picked plan (the latest by default): Spec, Plan (with the picker of the plans, newest first, when there are two or more, `+ Nouveau plan`, and the plan's folder name under it), one row per stage, Revue finale, each with its marker on a rail (on the desktop and the mobile app, vector circles: green ticked when done, orange filled while a live session works on it, orange ring for the step at hand, grey ring later; on the terminal, `✓ ◉ ○` glyphs on a `│` rail). Under each row, its latest session on one caption line (date, duration, session, and its status pill unless done); the earlier ones fold behind `▸ N essai(s) précédent(s)`. Under the step at hand stand its buttons and, on one truncated line, its prompt, in a frame; under them, the `⚡ Autopilot` button that runs the rest of the feature with no click, with its `☐ Test navigateur` checkbox. A band above the prompt names on one line what this session does (`Stage 2 — web 1/3`, `Plan`, `Spec`, `Revue du plan`, `Revue finale 3/3`, `Autopilot · Stage 2 — web 1/3`), always the step its run was started on, never the plan's next stage (a stage whose boxes are all ticked is still that session's until its commit), the feature, a status pill with the run's duration, the context tokens of the session (`42k tokens`, as the status line counts them), the count of the other live sessions, and the button that opens or closes the pane. Once the run is over (its commit made), the band also carries the primary button of the plan's next step, so the pane need not be opened; an autopilot that stopped carries `Reprendre l'autopilot` instead.

## What it shows

| Column | Source |
|---|---|
| Models | `selo-flow.yaml`'s `models` (the preset's name, a block map or an inline map), every role on the `standard` preset unless the file names another model |
| Branch | `git rev-parse --abbrev-ref HEAD`; its uncommitted files, every line of `git status --porcelain`; the stages' SHAs from the last 2000 commits of `git log` |
| Feature slug and title | `.planning/features/{slug}/00_spec.md` (title, status), else the plan's title |
| Plans | Every `dev-plans/*/plan.md`, newest first by folder name (its timestamp); the card, its state and the tiles follow the plan picked in the card, the latest until another is picked (kept for the session). While a live `write-plan {slug}` session writes a new plan whose folder is not there yet (the latest plan is committed), the card shows that plan on its way instead: `nouveau plan en cours`, its `Plan` row running, no picker and no prompt to prepare. A plan that appears is followed at once, whatever plan was picked |
| State | `spec seule`, `plan prêt`, `en cours`, `à valider`, `plan finalisé` (every stage and the Validation's `Review` ticked, the optional items left as they are), from the followed plan: its Progress ticks and its Validation checklist |
| Stages | One line per `### Stage N — …` of the plan's Progress, with the short SHA of the stage's commit once its subject (`Commit:` line) is on the branch |
| Draft | `(brouillon)` while `plan.md` is untracked, as the planning rule defines a draft |
| Spec | `spec brouillon` (`Draft`) or `spec validée` (`Approved`), from the spec header, for a feature with no plan yet |
| Timeline | `Spec` (`présente`, `absente`), `Plan` (`brouillon`, `commité`), one `Stage N — …` per stage (its count, then its short SHA), `Revue finale` (the Validation count, a declined item `[-]` counted as settled; done once `Review` is ticked); the step at hand is the one the primary button prepares |
| Runs | Under each step, the latest: `16/10 00:21 · 14 min · session 7f0772df`, with an `● en cours · 14 min`, `○ attend une réponse` or `! interrompue` pill when not done; the earlier ones behind `▸ N essai(s) précédent(s)`. The live ones are also listed above the cards, one line each, which unfolds the feature on the run's plan on a click |
| Autopilot | One run for the whole pipeline, `Autopilot · {step}` in the session list and the band, its step the one its subagent at work is on; each step row keeps the run of the subagent that worked on it (the pipeline's own run is on no row), and the marker of the pipeline's step turns while no subagent is live yet. Its pill: `● en cours · 1 h 12`, then `✓ terminé`, or `! arrêté · à reprendre` |

The source of truth stays the files and git. The board is rescanned every 10 seconds, after each `git commit` run through Bash, and at the end of each turn. A stage whose commit reaches the branch, or a Validation checklist that becomes complete, raises a toast.

## The one thing the mod keeps

The runs live in the mod's own store (`$.store`, a JSON file under the user's Claude Code directory, shared by every session, never in the repository). A run is written when a prompt starting with `/selo-flow:implement`, `/selo-flow:write-plan`, `/selo-flow:write-spec`, `/selo-flow:review` or `/selo-flow:autopilot`, or a call of one of these skills through the `Skill` tool from the session's main loop (a session driven by a brief calls them that way, never from a typed prompt), or a brief given to a subagent through the `Agent` tool from the main loop whose first `/selo-flow:` line is such a command (the autopilot's steps), names a feature (a `.planning/features/{slug}` path, or a bare slug, alone or before an option, for `write-plan`, `write-spec` and `autopilot`), with the timeline step it lands on, frozen at that moment (`spec`, `plan`, `stage:N` the stage the prompt names (`— stage 2 (web)`), else the next stage of the plan, `review` for `/selo-flow:review {plan folder}`). A `write-spec` or an `autopilot` given a free request names no feature yet: its run is written without one (`nouvelle feature`), and takes the slug from the scope of its spec's commit (`docs({slug}): spec — …`). A run belongs to the loop that started it: the session's main loop, or the subagent the brief was given to (the run carries its id). It is set to `running` at each turn start of its loop (an `interrupted` run comes back with it), `waiting` at each turn end (a subagent that returns without committing leaves its run `waiting` until the session ends), `done` once its loop runs a successful `git commit` (every selo-flow skill ends its job with its commit, an `interrupted` run too); a chained run (`— stages 2-3 (web, e2e), chained`) moves to its next stage at each stage commit instead, and is done at its last one; `interrupted` when the session ends before that or goes silent for a day. A finished run stays as history under its step; a run older than a month is dropped. Each `/selo-flow:` prompt or skill call of a session starts a new run. An `autopilot` run is the pipeline: it starts at the feature's step (the spec, from a request), moves to the step of each subagent its main loop spawns with a `/selo-flow:` brief, takes the feature and the plan folder those name, and ends with its main loop's turn: `done` when the last subagent committed, `interrupted` otherwise (a blocker, an abort), its subagents left waiting interrupted with it. A turn that ends while its last subagent still works in the background (resumed to finish its job) leaves the pipeline live, and the hand-back's turn goes on with it; a pipeline interrupted at such a turn's end comes back at the next one. A session that works without the workflow (a free request, no `/selo-flow:` command, no selo-flow skill) is followed too: its first prompt (a slash command apart) writes an `off-workflow` run, with no feature and no step (`Session libre · hors workflow` in the band and the live sessions), which goes through the same statuses and phases; its commit makes it `done` without taking the commit's scope as a feature, and the next free prompt starts a new one. A session that already has a selo-flow run keeps it: a free prompt there (the answer to a commit question) records nothing. To run a selo-flow step, use the pane's button, which prepares the exact command. A run carries the repository's git common dir (`git rev-parse --git-common-dir`, absolute), and the board lists the runs of its repository whatever the worktree each session runs in: a session working in a worktree shows on the board opened at the main checkout. The plan folder itself lives on the worktree's branch, so that board may not have the feature's row yet: the run is then listed with the live sessions only, until the branch is merged.

## The export for companion apps

At each rescan, the board is also written as JSON for an app outside Claude Code (a dashboard that draws the pane on its own): `{CLAUDE_CONFIG_DIR, else ~/.claude}/selo-flow-board/{root}.json`, one file per project root, the root named as `~/.claude/projects` names its folders (every character but a letter or a digit as `-`: `C:\WS\ia-projects\claude-companion` is `C--WS-ia-projects-claude-companion.json`). A worktree is a root of its own, so it has its own file. A companion lists that folder to find every project. The content is `SeloFlowBoardExport` of `types/index.d.ts` (`schemaVersion: 3`): the branch line, the models, the live sessions, the project's `activity` and its `sessions`, and each feature on the plan the pane follows by default (the latest, or the new one on its way) with its timeline rows (title, detail, marker, runs) and the prompts its buttons prepare, `null` where the pane offers none; `markers` are what the pane's checkboxes add at the end of a prompt. Each run carries a `phase`, set at each turn's end from the turn's final text, as the workflow rules shape it: `awaiting-commit` when it closes on a code block whose first line is a `{type}({scope}): …` subject (the message, in `pendingCommit`), `job-done` when it holds the done footer (its `> ` recap line and its commits, in `recap`) or its run is done, `awaiting-answer` otherwise; `working` while a turn runs, `interrupted` with the run. `sessions` is each session's latest main-loop run, `phase` always set, an off-workflow one with `command` and `step` `off-workflow` and `feature` and `folder` null; `activity` is the one that most needs the person (a commit question, then another question, then a turn at work), else the latest, `idle` without any. Whether a job done was seen is the companion's to keep: the board does not close a session. The file is rewritten whole, not atomically: a reader that cannot parse it reads it again at its next poll. A failed write never stops the board. The file is as fresh as the last session of the project with the mod: none open, it stays at its last scan (`scannedAt`).

## Buttons

- The feature row unfolds its timeline; a line of the live sessions block unfolds the feature it works on. The filter chips keep the matching features; the folded line of the finalized features shows them.
- The row's primary button fills the prompt box with the next command: `write-spec` for an empty feature, none for an area with its spec and no plan (`+ Nouveau plan` starts one), `write-plan` for a draft plan, `implement {plan folder} — stage {N} ({title})` for the next stage, `/selo-flow:review {plan folder}` once every stage is ticked and the last stage left `Review` open, none once the plan is finalized. Enter sends it. Where no prompt box takes it, the prompt is copied instead. The same button stands in the band once this session's run is over.
- `⚡ Autopilot`, under the framed step of a feature with a spec, prepares `/selo-flow:autopilot {plan folder}` (its stages left, the last one reviewing the whole plan; a draft plan is committed as it stands) for a feature with a plan. `☐ Test navigateur` next to it adds ` — with browser test`. An earlier stop (` — until spec`, ` — until plan`) is typed at the end of the prompt before Enter. `⚡ Nouvelle feature`, in the header, fills `/selo-flow:autopilot ` for a feature that does not exist yet: the request is typed after it. While an autopilot works on a feature, its card offers no prompt (the step says `Autopilot en cours sur cette feature`); the band of the autopilot's session offers `Reprendre l'autopilot` once it stopped (`/selo-flow:autopilot {plan folder | slug}`, resumed where the Progress is).
- In the framed step: `Tout d'un coup (stages N–M)`, when several stages remain, prepares `implement {plan folder} — stages N-M (…), chained`, every remaining stage in one session, one commit each; `⧉ Copier` copies the step's prompt; on `Revue finale`, `Marquer comme fait` ticks the Validation's `Review` item in `plan.md` without running the review (a `[-]` too): the plan is finalized, the tick is left uncommitted; `Revue du plan` prepares `/selo-flow:review plan {plan folder}`.
- On the Plan row: the picker of the plans (two or more), and `+ Nouveau plan`, which prepares `/selo-flow:write-plan {slug}` (a new plan folder of the same spec). Under a step, `▸ N essai(s) précédent(s)` unfolds its earlier sessions.
- `⚙ Modèles` opens the configuration screen: one line per role of the manifest (`planner`, `implementer`, `reviewer`, `runner`, `explorer`) with its model (`opus`, `sonnet`, `haiku`, `fable`; on the mobile app, a press moves to the next one). A change writes `selo-flow.yaml`'s `models` as `init` does (`models: standard` when every role is the preset's, else `preset: standard` and the roles that differ), left uncommitted; it applies to the next step launched, not to an autopilot already running.
- `⟳` rescans now.
- The band’s `Ouvrir le tableau` / `Fermer le tableau` toggles the pane; closing it from the engine’s own mark flips the button too.

## Running it

- `/selo-flow-board` opens the pane in any session; on the desktop and in an IDE it opens by itself when the project has `.planning/features`.
- While developing: `claude --plugin-dir C:\WS\webapp-factory\plugins\selo-flow-board` in a project, or the folder in `CLAUDE_CODE_PLUGIN_DIRS` for a session the desktop app starts. The engine then lays its type declarations in `.claude-plugin/types/` (ignored by git).
- Installed: `/plugin install selo-flow-board --marketplace <selo-flow marketplace>`.

## Checks

```bash
claude plugin validate plugins/selo-flow-board
```

```bash
claude plugin test plugins/selo-flow-board
```

The tests cover the parser (`hooks/planning.ts`) directly and the hooks through the engine's test kit, with the project, git and the store answered from memory, on the terminal and desktop surfaces.

## Limits

- Draft detection relies on `git status` paths relative to the repository root: a project rooted in a sub-folder of its repository shows no draft.
- The stage SHA is matched on the commit subject the plan announces; a stage committed under another subject shows `non committé`; so does one older than the last 2000 commits.
- The branch line counts the whole repository: in a project rooted in a sub-folder, the uncommitted files outside the project count too.
- `base_branch` is read with a line match on `selo-flow.yaml`, not a YAML parse: a nested or multi-line value falls back to `main`.
- `models` is read and written line by line, not as YAML: the comments inside its block are dropped when the screen rewrites it, and the roles and the `standard` preset are a copy of `scripts/manifest.mjs`'s, kept in step by hand.
- The mobile app draws no picker: there a card shows the latest plan.
- A `write-plan {slug}` run names no plan folder: once over, it is listed under the latest plan.
- A subagent the autopilot spawns to fix a review's findings (`implement fix findings of … on {plan folder}`) names no stage: its run lands on the plan's next stage, not on the one reviewed.
- The autopilot's end is read from its main loop's turn: a pipeline whose session ends a turn before its report (a question the orchestrator should not ask) shows as `arrêté`.
